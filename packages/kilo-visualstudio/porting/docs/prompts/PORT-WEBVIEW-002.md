Integrate the strongly-typed WebView DTOs generated by **PORT-WEBVIEW-001** into the existing Visual Studio extension WebView communication layer.

## Architectural Decisions

### 1. SSE vs WebView Distinction

**Decision**: SSE events and WebView messages are treated as separate protocols.

**Rationale**:
- SSE events come from the backend API (NSwag-generated types)
- WebView messages are extension↔webview communication (generated DTOs)
- Both use `Newtonsoft.Json` with `KiloJsonSerializer`

**Implementation**:
- SSE: `SSEHelper.cs` → `SseEventDeserializer` → `PolymorphicDeserializer`
- WebView: `WebViewMessageFactory` available for typed deserialization

### 2. Polymorphic Deserialization Pattern

**Decision**: Use explicit discriminator inspection without `JsonConverter` inheritance.

**Pattern**:
```csharp
JSON
  ↓
JObject/JToken
  ↓
discriminator inspection (type, role, status)
  ↓
explicit ToObject<T> for concrete type
```

**Implementation**: `PolymorphicDeserializer.cs` with methods for:
- `DeserializePart` - Part subtypes
- `DeserializeToolState` - ToolState subtypes
- `DeserializeSessionMessage` - Message subtypes
- `DeserializeFilePartSource` - FilePartSource subtypes
- SSE event deserializers

### 3. JToken Fallback for Dynamic Access

**Decision**: Use `JObject.Parse(obj.ToJson())` only when accessing properties not available on the strongly-typed base class.

**Rationale**: The NSwag-generated `Message` base class is polymorphic without concrete properties. Accessing `id`, `sessionID`, `role`, etc. requires either:
1. Deserializing to the concrete type (`SessionMessageAssistant`, `SessionMessageUser`)
2. Using `JObject` for dynamic access

**Implementation**: `SSEHelper.cs` uses `JObject.Parse(info.ToJson())` for dynamic property access after polymorphic deserialization.

## Known Limitations

### 1. Incremental Integration

**Finding**: The generated DTOs are available and the `DeserializeWebViewMessage<T>` helper is implemented, but not all message handlers have been migrated to use typed deserialization.

**Reason**: PORT-WEBVIEW-002 establishes the integration pattern and validates the generated artifacts. Full migration of all message handlers is incremental work that can be done without breaking existing functionality.

**Impact**: None - existing functionality continues to work. The typed DTOs and helper method are available for future integration.

### 2. System.Text.Json in KiloWebViewControl

**Finding**: `KiloWebViewControl` uses `System.Text.Json.JsonElement` for incoming WebView messages.

**Reason**: This is separate from the SSE pipeline and was the existing implementation. The `DeserializeWebViewMessage<T>` helper bridges this gap by converting to `JToken` for `WebViewMessageFactory`.

**Impact**: Minimal overhead from JSON conversion. Migration to native `Newtonsoft.Json` parsing can be done incrementally if desired.
