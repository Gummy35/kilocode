## Objective

Integrate the strongly-typed WebView DTOs generated by **PORT-WEBVIEW-001** into the existing Visual Studio extension WebView communication layer.

The objective is to establish a production-ready transport boundary in which WebView JSON messages are deserialized using the generated C# DTOs and the existing shared **Newtonsoft.Json** infrastructure, while preserving the WebView protocol defined by the VS Code extension exactly.

This task must also identify and port the VS Code tests that validate WebView protocol behavior and can be meaningfully reproduced in the Visual Studio extension.

The VS Code implementation remains the **sole source of truth** for the WebView protocol.

---

## Source of Truth

The authoritative protocol is the current VS Code extension implementation.

The following must be treated as authoritative:

1. VS Code TypeScript message definitions;
2. VS Code WebView message handlers;
3. VS Code WebView serialization/deserialization behavior;
4. VS Code tests covering the relevant protocol;
5. The generated `WebViewContract.json` produced by PORT-WEBVIEW-001.

`WebViewContract.json` is a generated representation of the VS Code contract.

It must not be manually modified to accommodate the Visual Studio implementation.

If the generated contract and the VS Code implementation disagree, investigate the extractor rather than changing the contract manually.

## 2. Integrate generated WebView DTOs

Use the DTOs generated by PORT-WEBVIEW-001.

Do not create manually maintained duplicates of generated DTOs.

Do not manually recreate individual WebView protocol messages in C#.

The intended architecture is:

```text
VS Code WebView
       │
       │ JSON
       ▼
Visual Studio WebView boundary
       │
       ▼
Newtonsoft.Json
       │
       ▼
Generated WebView DTO
       │
       ▼
Handler / Service
```

Where polymorphism is required:

```text
JSON
 │
 ▼
JObject / JToken
 │
 ▼
discriminator
 │
 ▼
generated concrete DTO
```

Use the existing centralized discriminator architecture established by PORT-INFRA-003.

# 3. Newtonsoft.Json

The WebView protocol must use **Newtonsoft.Json**.

Do not introduce System.Text.Json into the WebView protocol serialization/deserialization layer.

Reuse:

```text
KiloJsonSerializer
```

and the existing shared serializer configuration.

There must not be a second independent serializer configuration for WebView DTOs.

The following must remain true:

```text
NSwag API
     │
     ├── Newtonsoft.Json
     │
     └── KiloJsonSerializer

SSE
     │
     ├── Newtonsoft.Json
     │
     └── KiloJsonSerializer

WebView
     │
     ├── Newtonsoft.Json
     │
     └── KiloJsonSerializer
```

The goal is one JSON implementation and one shared serializer configuration across the C# extension architecture.

---

# 4. Polymorphism

Use the explicit discriminator factory approach established by PORT-INFRA-003.

Do not reintroduce:

* `PartConverter`;
* `ToolStateConverter`;
* `MessageConverter`;
* generic `JsonConverter<T>` infrastructure merely to solve WebView polymorphism.

Where generated WebView DTOs contain discriminated unions, use explicit discriminator inspection.

The implementation must support nested polymorphism where required by the generated contract.

Examples include structures equivalent to:

```text
Message
 └── role
      ├── user
      └── assistant
```

or:

```text
Part
 └── type
      ├── text
      ├── tool
      ├── file
      └── ...
```

The exact types must be determined from the generated contract rather than hard-coded from this task description.

# 5. Preserve the VS Code wire protocol

The Visual Studio extension must consume and produce the same JSON protocol as the VS Code extension.

Do not:

* rename JSON properties;
* change discriminator values;
* change optional/required semantics;
* introduce Visual Studio-specific protocol fields;
* remove fields because they are not currently used;
* change the message envelope;
* create a Visual Studio-specific version of the protocol.

For example, if the VS Code protocol contains:

```json
{
  "type": "someMessage",
  "properties": {
    "sessionID": "..."
  }
}
```

the Visual Studio implementation must preserve that structure.

The generated DTO may use a C# property such as:

```csharp
[JsonProperty("sessionID")]
public string SessionId { get; set; }
```

but the wire representation must remain:

```json
"sessionID"
```

# 6. Transport DTO vs Domain Model

Do not assume that every generated WebView DTO should become a business-domain object.

The generated DTOs represent the **transport contract**.

Where appropriate:

```text
WebView JSON
     ↓
Generated DTO
     ↓
Domain/service model
     ↓
Business logic
```

is preferable to contaminating the transport DTO with Visual Studio-specific behavior.

However, do not introduce unnecessary mapping layers.

If the generated DTO already provides exactly what a handler needs, use it directly.

A mapping layer should only be introduced where there is a real semantic distinction between:

* transport contract;
* domain model.
